# EduAlerta — Diccionario de datos

**Versión:** 0.1  
**Fecha:** 12 de octubre de 2026  
**Estado:** Borrador técnico para revisión  
**Documento relacionado:** `modelo-conceptual-datos.md`

## 1. Propósito

Este diccionario traduce el modelo conceptual de EduAlerta en una propuesta de tablas, columnas, tipos de datos y restricciones pensadas para PostgreSQL. Debe revisarse y aprobarse antes de escribir migraciones SQL o entidades JPA.

**Importante:** este diccionario describe el diseño propuesto; no implica que la base de datos ya exista. Los tipos son propuestas iniciales y algunas reglas requieren validación institucional.

## 2. Convenciones generales

- Los nombres de tablas y columnas usan `snake_case`, en singular o según el nombre documentado, sin tildes ni espacios.
- Las claves principales se denominan `id` y se proponen como `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Las claves foráneas conservan el nombre de la entidad relacionada seguido de `_id`, por ejemplo `estudiante_id`.
- Los textos breves usan `VARCHAR(n)`; los textos de extensión variable usan `TEXT`.
- Las fechas de eventos que ocurren en un momento concreto usan `TIMESTAMPTZ`. PostgreSQL conserva el instante y permite representarlo en la zona horaria de la aplicación.
- Las fechas de calendario sin hora usan `DATE`.
- Los valores monetarios no están dentro del alcance de este sistema.
- Para niveles, roles y estados se propone `VARCHAR` más restricciones `CHECK` o validación equivalente en la aplicación, en vez de crear tipos nativos de PostgreSQL desde el inicio. Esto facilita futuras migraciones.
- Los campos que contienen información estructurada variable podrán usar `JSONB` solo cuando exista una necesidad concreta. No se usará como sustituto de relaciones que deban consultarse o validarse de forma normalizada.
- Las contraseñas se guardan como hash, no como texto plano.
- La aplicación debe validar también las reglas de negocio. Una validación del frontend nunca reemplaza la validación del backend o las restricciones de la base de datos.

### Abreviaturas

- **PK:** clave primaria.
- **FK:** clave foránea.
- **UQ:** valor único.
- **NN:** no nulo (`NOT NULL`).
- **NULL:** dato opcional.
- **Propuesta:** tipo o restricción sugeridos, pendientes de aprobación.

## 3. Entidades compartidas

### 3.1 Tabla `usuario`

Almacena las cuentas que pueden autenticarse en EduAlerta.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador interno de la cuenta. |
| `nombres` | `VARCHAR(100)` | NN | Nombres de la persona. |
| `apellidos` | `VARCHAR(100)` | NN | Apellidos de la persona. |
| `correo` | `VARCHAR(254)` | NN, UQ | Correo normalizado para inicio de sesión y comunicaciones autorizadas. |
| `password_hash` | `VARCHAR(255)` | NN | Hash de contraseña generado con un algoritmo apropiado para contraseñas. Nunca almacenar la contraseña original. |
| `rol` | `VARCHAR(20)` | NN, CHECK | Uno de `administrador`, `docente`, `orientador` o `estudiante`. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Estado de la cuenta: propuesta inicial `activo`, `inactivo` o `bloqueado`. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha y hora de creación. |
| `actualizado_en` | `TIMESTAMPTZ` | NULL | Fecha y hora de la última modificación. |

**Reglas y observaciones:** normalizar el correo (por ejemplo, quitar espacios externos y comparar en minúsculas). La unicidad debe ser insensible a mayúsculas/minúsculas, ya sea mediante índice apropiado o una regla de normalización. No registrar contraseñas, tokens o secretos en logs. La recuperación de contraseña real se definirá cuando se implemente el servicio de autenticación.

### 3.2 Tabla `estudiante`

Almacena la ficha escolar mínima del estudiante. Puede existir sin cuenta de acceso vinculada.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador interno de la ficha. |
| `usuario_id` | `BIGINT` | FK a `usuario.id`, NULL, UQ | Cuenta de acceso asociada, si existe. Un usuario estudiante no debe vincularse con más de una ficha. La coherencia entre el rol del usuario y esta relación se valida en el backend. |
| `codigo_estudiantil` | `VARCHAR(50)` | NN, UQ | Código institucional del estudiante. Confirmar si la institución dispone de uno. |
| `nombres` | `VARCHAR(100)` | NN | Nombres del estudiante. |
| `apellidos` | `VARCHAR(100)` | NN | Apellidos del estudiante. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Estado escolar, propuesta inicial: `activo`, `inactivo`, `egresado` o `retirado`. Definir con la institución. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de creación de la ficha. |
| `actualizado_en` | `TIMESTAMPTZ` | NULL | Fecha de modificación. |

**Reglas y observaciones:** no se incluyen inicialmente dirección, documento de identidad, datos familiares ni fecha de nacimiento porque todavía no se ha justificado su necesidad. La política de identificación y los datos obligatorios se deben validar antes de implementar. En el esquema físico puede ser preferible que `codigo_estudiantil` tenga unicidad dentro de la institución y no una unicidad global, si se habilitan múltiples instituciones en el futuro.

### 3.3 Tabla `grupo_escolar`

Representa un grupo escolar para un año lectivo específico, como 10.º A de 2026.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del grupo. |
| `nombre` | `VARCHAR(30)` | NN | Nombre visible del grupo, por ejemplo `10A`. |
| `grado` | `VARCHAR(10)` | NN | Grado escolar, por ejemplo `10` u `11`. |
| `seccion` | `VARCHAR(10)` | NULL | Sección o letra del grupo, si se maneja por separado. |
| `anio_lectivo` | `SMALLINT` | NN | Año lectivo al que pertenece el grupo. |
| `jornada` | `VARCHAR(30)` | NULL | Jornada académica, si aplica. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `activo` o `inactivo`. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de creación del grupo. |

**Restricciones propuestas:** evitar duplicados para la combinación que la institución considere única, normalmente `anio_lectivo`, `grado`, `seccion` y `jornada`. Antes de implementar, decidir si `nombre` sustituye `seccion` o si se necesitan ambos campos.

### 3.4 Tabla `matricula`

Vincula a un estudiante con un grupo escolar. Su historial permite conservar los cambios de grado y año lectivo.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la matrícula. |
| `estudiante_id` | `BIGINT` | FK a `estudiante.id`, NN | Estudiante matriculado. |
| `grupo_escolar_id` | `BIGINT` | FK a `grupo_escolar.id`, NN | Grupo en el que está matriculado durante el año lectivo correspondiente. |
| `fecha_matricula` | `DATE` | NN | Fecha de formalización de la matrícula. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `activa`, `finalizada`, `cancelada` o `trasladada`. Validar estados institucionales. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de registro en el sistema. |
| `actualizado_en` | `TIMESTAMPTZ` | NULL | Fecha de actualización. |

**Restricciones propuestas:** no duplicar matrícula del mismo estudiante en el mismo grupo. Validar que no existan dos matrículas activas para un mismo estudiante en el mismo año lectivo, salvo excepción institucional. El año lectivo puede obtenerse del grupo, por lo que no se duplica inicialmente en la matrícula.

### 3.5 Tabla `asignatura`

Catálogo de asignaturas para el rendimiento académico.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la asignatura. |
| `codigo` | `VARCHAR(30)` | UQ, NULL | Código de la asignatura si existe en la institución. |
| `nombre` | `VARCHAR(100)` | NN | Nombre de la materia. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `activa` o `inactiva`. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de creación. |

### 3.6 Tabla `periodo_academico`

Representa un período de evaluación dentro de un año lectivo.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del período. |
| `anio_lectivo` | `SMALLINT` | NN | Año lectivo del período. |
| `nombre` | `VARCHAR(30)` | NN | Nombre visible, por ejemplo `Periodo 1`. |
| `fecha_inicio` | `DATE` | NN | Inicio del período. |
| `fecha_fin` | `DATE` | NN | Finalización del período. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `planificado`, `activo` o `cerrado`. |

**Restricciones propuestas:** unicidad de `anio_lectivo` + `nombre`; `fecha_fin` no puede ser anterior a `fecha_inicio`. La correspondencia entre el año lectivo del período y el año de la matrícula debe validarse en la aplicación o mediante una estrategia de base de datos definida posteriormente.

### 3.7 Tabla `rendimiento_academico`

Guarda una nota resumida por matrícula, asignatura y período académico. No representa cada evaluación individual ni cada tarea.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del registro de rendimiento. |
| `matricula_id` | `BIGINT` | FK a `matricula.id`, NN | Matrícula a la que corresponde el rendimiento. |
| `asignatura_id` | `BIGINT` | FK a `asignatura.id`, NN | Asignatura evaluada. |
| `periodo_academico_id` | `BIGINT` | FK a `periodo_academico.id`, NN | Período de evaluación. |
| `nota_promedio` | `NUMERIC(5,2)` | NN | Nota resumida del estudiante para esa combinación. La escala máxima y mínima debe confirmarse antes de imponer un `CHECK` definitivo. |
| `observacion` | `TEXT` | NULL | Observación académica breve, si se necesita y existe autorización para almacenarla. |
| `actualizado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de la última actualización del resumen. |

**Restricción propuesta:** `UNIQUE (matricula_id, asignatura_id, periodo_academico_id)`. Si después se requieren calificaciones de tareas, evaluaciones o actividades, diseñar una entidad separada; no añadirlas como múltiples registros ambiguos en esta tabla.

### 3.8 Tabla `registro_asistencia`

Guarda el estado diario de asistencia de una matrícula. El diseño inicial no controla asistencia por cada período de clase.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del registro de asistencia. |
| `matricula_id` | `BIGINT` | FK a `matricula.id`, NN | Matrícula correspondiente al registro. |
| `fecha` | `DATE` | NN | Día escolar al que corresponde la asistencia. |
| `estado` | `VARCHAR(30)` | NN, CHECK | `Presente`, `Retardo`, `Ausencia justificada` o `Ausencia sin justificar`. |
| `observacion` | `TEXT` | NULL | Nota breve, evitando información sensible innecesaria. |
| `registrado_por_usuario_id` | `BIGINT` | FK a `usuario.id`, NULL | Usuario que registró el dato, si aplica. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Momento en que se guardó el registro. |

**Restricción propuesta:** `UNIQUE (matricula_id, fecha)`. Si se decide que la asistencia debe registrarse por clase o sesión, este modelo habrá de revisarse antes de implementar la tabla.

## 4. Entidades de Alertas Tempranas

### 4.1 Tabla `evaluacion_riesgo`

Conserva el resultado de una evaluación del riesgo de deserción. No constituye una certeza ni una decisión automatizada sobre el estudiante.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la evaluación. |
| `matricula_id` | `BIGINT` | FK a `matricula.id`, NN | Matrícula evaluada. |
| `evaluado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha y hora en que se calculó el resultado. |
| `nivel_riesgo` | `VARCHAR(10)` | NN, CHECK | Uno de `bajo`, `medio` o `alto`. |
| `probabilidad_estimada` | `NUMERIC(5,4)` | NULL, CHECK | Probabilidad entre 0 y 1, solo si el método produce una probabilidad interpretable. No se debe inventar una probabilidad a partir de una simple etiqueta heurística. |
| `metodo` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `heuristica` o `modelo`. |
| `version_metodo` | `VARCHAR(60)` | NN | Versión identificable de la regla, modelo o configuración utilizada. |
| `indicadores_json` | `JSONB` | NULL | Resumen mínimo de indicadores usados, si es necesario explicar el resultado. Evitar copiar datos personales que ya están almacenados en otras tablas. |
| `observacion_tecnica` | `TEXT` | NULL | Nota técnica breve sobre la evaluación, sin reemplazar una explicación al usuario. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Momento en que el registro fue persistido. |

**Restricciones propuestas:** si `probabilidad_estimada` no es nula, debe estar entre 0 y 1. Los umbrales que convierten un puntaje a nivel de riesgo deben definirse y validarse por separado. Se conserva cada evaluación en lugar de sobrescribir la anterior.

### 4.2 Tabla `alerta_temprana`

Representa una señal que requiere revisión y seguimiento por personal autorizado.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la alerta. |
| `matricula_id` | `BIGINT` | FK a `matricula.id`, NN | Matrícula a la que corresponde la alerta. |
| `evaluacion_riesgo_id` | `BIGINT` | FK a `evaluacion_riesgo.id`, NULL | Evaluación que originó la alerta, si corresponde. |
| `tipo_senal` | `VARCHAR(30)` | NN | Categoría de la señal, por ejemplo `asistencia`, `rendimiento`, `combinada` o `manual`. Catálogo por validar. |
| `descripcion` | `TEXT` | NN | Explicación breve y comprensible de por qué se generó la alerta. |
| `nivel_riesgo` | `VARCHAR(10)` | NN, CHECK | `bajo`, `medio` o `alto`. Puede conservar el nivel relevante al momento de generar la alerta. |
| `origen` | `VARCHAR(15)` | NN, CHECK | `automatica` o `manual`. |
| `estado` | `VARCHAR(20)` | NN, CHECK | `Nueva`, `En seguimiento` o `Revisada`. |
| `asignado_a_usuario_id` | `BIGINT` | FK a `usuario.id`, NULL | Usuario responsable del seguimiento, si ya fue asignado. |
| `creada_por_usuario_id` | `BIGINT` | FK a `usuario.id`, NULL | Usuario que creó la alerta manualmente. Puede ser nulo para alertas automáticas. |
| `creada_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha y hora de creación. |
| `actualizada_en` | `TIMESTAMPTZ` | NULL | Fecha de la última actualización. |

**Reglas propuestas:** una alerta manual debe identificar al usuario creador; una alerta automática debe guardar el origen técnico que la produjo. La regla exacta de `CHECK` se definirá en el esquema físico. La persona asignada debe tener un rol autorizado y su relación con la institución o grupo debe validarse en el backend. Cambiar a `Revisada` no equivale a declarar resuelta la situación.

### 4.3 Tabla `seguimiento_alerta`

Conserva las acciones y observaciones realizadas frente a una alerta.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del seguimiento. |
| `alerta_temprana_id` | `BIGINT` | FK a `alerta_temprana.id`, NN | Alerta a la que pertenece el seguimiento. |
| `usuario_id` | `BIGINT` | FK a `usuario.id`, NN | Usuario autenticado que registra el seguimiento. |
| `accion_realizada` | `VARCHAR(120)` | NN | Acción realizada o tipo de intervención documentada. |
| `observaciones` | `TEXT` | NN | Nota breve sobre el seguimiento. Evitar detalles personales innecesarios. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha y hora del seguimiento. |

Los seguimientos deben tratarse como registros históricos. Si se requiere auditar todos los cambios de estado, se diseñará explícitamente una tabla de historial de estados o un mecanismo de auditoría; no se debe asumir que esta tabla cubre por sí sola todos los cambios.

## 5. Entidades de Orientación Vocacional

### 5.1 Tabla `version_test`

Identifica una versión del instrumento vocacional y de su metodología de cálculo.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la versión. |
| `codigo_version` | `VARCHAR(30)` | NN, UQ | Código, por ejemplo `vocacional-v1`. |
| `nombre` | `VARCHAR(120)` | NN | Nombre visible del instrumento. |
| `descripcion` | `TEXT` | NULL | Propósito e indicaciones. |
| `version_calculo` | `VARCHAR(60)` | NN | Versión del algoritmo de puntuación usado por esta versión. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `borrador`, `activa` o `retirada`. |
| `creada_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha de creación de la versión. |
| `publicada_en` | `TIMESTAMPTZ` | NULL | Fecha de publicación, si llega a estar activa. |

Una versión publicada que ya tenga intentos asociados no debe modificarse de manera que altere la interpretación histórica. Los cambios sustanciales deben crear una nueva versión.

### 5.2 Tabla `pregunta_vocacional`

Contiene las preguntas que componen una versión específica del test.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la pregunta. |
| `version_test_id` | `BIGINT` | FK a `version_test.id`, NN | Versión del test a la que pertenece. |
| `codigo_pregunta` | `VARCHAR(30)` | NN | Código estable dentro de la versión. |
| `enunciado` | `TEXT` | NN | Texto presentado al estudiante. |
| `orden` | `SMALLINT` | NN | Posición de la pregunta. |
| `activa` | `BOOLEAN` | NN, default `TRUE` | Indica si se presenta en la versión. |

**Restricciones propuestas:** `UNIQUE (version_test_id, codigo_pregunta)` y `UNIQUE (version_test_id, orden)`. Las preguntas publicadas no se deben editar de forma que cambien los intentos históricos; publicar una nueva versión cuando sea necesario.

### 5.3 Tabla `opcion_vocacional`

Guarda las opciones disponibles para cada pregunta y su contribución al cálculo del resultado.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la opción. |
| `pregunta_vocacional_id` | `BIGINT` | FK a `pregunta_vocacional.id`, NN | Pregunta a la que pertenece la opción. |
| `codigo_opcion` | `VARCHAR(10)` | NN | Código de la opción, por ejemplo `a`, `b`, `c` o `d`. |
| `etiqueta` | `TEXT` | NN | Texto mostrado al estudiante. |
| `area_codigo` | `VARCHAR(30)` | NN | Área vocacional a la que contribuye, por ejemplo `tecnologia`, `ciencia`, `creatividad`, `social` o `negocios`. Catálogo por validar. |
| `puntaje` | `NUMERIC(6,2)` | NN, default `1` | Puntos que aporta la opción a su área según la regla de cálculo definida. |
| `emoji` | `VARCHAR(16)` | NULL | Elemento visual opcional. Si no se necesita accesibilidad o presentación, puede omitirse del almacenamiento. |

**Restricción propuesta:** `UNIQUE (pregunta_vocacional_id, codigo_opcion)`. La opción seleccionada en una respuesta debe pertenecer a la pregunta contestada. Las áreas y pesos deben concordar con `version_calculo` y la lógica documentada.

### 5.4 Tabla `intento_vocacional`

Representa una ejecución del test por parte de un estudiante.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del intento. |
| `estudiante_id` | `BIGINT` | FK a `estudiante.id`, NN | Estudiante que realiza el test. |
| `version_test_id` | `BIGINT` | FK a `version_test.id`, NN | Versión exacta del instrumento. |
| `estado` | `VARCHAR(20)` | NN, CHECK | Propuesta inicial: `borrador`, `completo` o `abandonado`. |
| `iniciado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Momento de inicio. |
| `finalizado_en` | `TIMESTAMPTZ` | NULL | Momento de finalización, si se completó. |
| `creado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Momento de creación del registro. |

**Reglas propuestas:** los intentos completados conservan sus respuestas y resultados. No se debe reutilizar el mismo intento para una nueva realización. Al consultar intentos, el backend debe verificar que el usuario tiene acceso a los datos del estudiante relacionado.

### 5.5 Tabla `respuesta_vocacional`

Conserva la opción elegida para una pregunta dentro de un intento específico.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador de la respuesta. |
| `intento_vocacional_id` | `BIGINT` | FK a `intento_vocacional.id`, NN | Intento al que pertenece. |
| `pregunta_vocacional_id` | `BIGINT` | FK a `pregunta_vocacional.id`, NN | Pregunta que se respondió. |
| `opcion_vocacional_id` | `BIGINT` | FK a `opcion_vocacional.id`, NN | Opción elegida. |
| `respondida_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha y hora de registro de la respuesta. |

**Restricciones propuestas:** `UNIQUE (intento_vocacional_id, pregunta_vocacional_id)` para permitir una respuesta por pregunta e intento. Además, la aplicación o las restricciones adicionales de la base de datos deberán garantizar que la pregunta y la opción pertenecen a la versión del test usada por el intento y que la opción pertenece a la pregunta elegida.

### 5.6 Tabla `resultado_vocacional`

Guarda un resultado por área para un intento completado. Con cinco áreas, normalmente habrá cinco filas asociadas a un intento.

| Campo | Tipo PostgreSQL propuesto | Restricción | Descripción |
|---|---|---|---|
| `id` | `BIGINT` | PK, NN, identity | Identificador del resultado por área. |
| `intento_vocacional_id` | `BIGINT` | FK a `intento_vocacional.id`, NN | Intento que produjo el resultado. |
| `area_codigo` | `VARCHAR(30)` | NN | Código del área evaluada. |
| `puntaje_obtenido` | `NUMERIC(8,2)` | NN | Puntaje calculado para el área. |
| `puntaje_maximo` | `NUMERIC(8,2)` | NN | Puntaje máximo aplicable según la versión y sus preguntas. |
| `porcentaje` | `NUMERIC(5,2)` | NN | Porcentaje normalizado, si la regla permite calcularlo. Rango propuesto de 0 a 100. |
| `nivel_interes` | `VARCHAR(20)` | NULL | Etiqueta descriptiva derivada de los umbrales documentados, si se utiliza. |
| `version_calculo` | `VARCHAR(60)` | NN | Versión del algoritmo empleado para el cálculo. |
| `calculado_en` | `TIMESTAMPTZ` | NN, default `CURRENT_TIMESTAMP` | Fecha del cálculo. |

**Restricciones propuestas:** `UNIQUE (intento_vocacional_id, area_codigo)` y `CHECK (porcentaje >= 0 AND porcentaje <= 100)`. El `puntaje_maximo` debe ser mayor que cero si se calcula porcentaje. Los umbrales de `nivel_interes` deben documentarse antes de implementarlos.

## 6. Restricciones e integridad transversales

Las siguientes restricciones deben implementarse en la base de datos cuando sea posible y reforzarse en el backend:

1. **Claves foráneas:** impedir registros huérfanos. Antes de borrar físicamente una entidad, comprobar su impacto sobre el historial.
2. **Identidad del estudiante:** `estudiante.usuario_id` debe ser único y, cuando no sea nulo, apuntar a un usuario cuyo rol sea `estudiante`. La validación del rol asociado puede requerir lógica de servicio o un mecanismo explícito en la base de datos.
3. **Integridad de períodos:** la matrícula, el grupo y el período académico deben corresponder al mismo año lectivo cuando aplique.
4. **Integridad de alertas:** las evaluaciones vinculadas a una alerta deben corresponder a la misma matrícula que la alerta. Si se crea una alerta manual, debe quedar su creador; si es automática, debe conservar su origen.
5. **Integridad vocacional:** la pregunta y la opción contestadas deben pertenecer a la versión del test asociada al intento. Esta regla necesita validación de servicio o restricciones adicionales cuidadosamente diseñadas.
6. **Concurrencia:** las actualizaciones de estados y el guardado de intentos deben evitar pérdidas de información si se reciben solicitudes simultáneas.
7. **Autorización:** toda consulta o cambio sobre datos de estudiantes debe verificar permisos en el backend, incluso si el identificador viene de una ruta o cuerpo de solicitud.
8. **Auditoría:** definir cómo registrar cambios de rol, asignaciones y transiciones de estado. No guardar contraseñas, tokens ni contenido excesivo de información sensible en logs.

## 7. Índices sugeridos para revisar en el esquema físico

Los índices definitivos se elegirán después de definir las consultas de las API. Como punto de partida:

- `usuario(correo)` con unicidad insensible a mayúsculas/minúsculas.
- `estudiante(codigo_estudiantil)` con unicidad según la política institucional.
- `matricula(estudiante_id, estado)` para consultar las matrículas de un estudiante.
- `rendimiento_academico(matricula_id, periodo_academico_id)` para mostrar rendimiento por estudiante y período.
- `registro_asistencia(matricula_id, fecha)` para consultar historiales de asistencia.
- `evaluacion_riesgo(matricula_id, evaluado_en DESC)` para recuperar evaluaciones recientes.
- `alerta_temprana(estado, nivel_riesgo, creada_en DESC)` para los listados y filtros de alertas.
- `seguimiento_alerta(alerta_temprana_id, creado_en)` para reconstruir el seguimiento de una alerta.
- `intento_vocacional(estudiante_id, iniciado_en DESC)` para consultar el historial del estudiante.
- `respuesta_vocacional(intento_vocacional_id)` y `resultado_vocacional(intento_vocacional_id)` para recuperar los datos de cada intento.

Estos índices son recomendaciones iniciales, no una decisión definitiva de rendimiento. Se deben validar contra las consultas reales y evitar índices redundantes.

## 8. Reglas recomendadas para borrado y conservación

- Preferir la inactivación de usuarios, estudiantes, grupos, asignaturas y versiones de test cuando exista historial asociado.
- No borrar en cascada evaluaciones de riesgo, alertas, seguimientos ni intentos vocacionales como consecuencia de desactivar un usuario o estudiante.
- Definir con la institución los plazos de conservación y las condiciones legales para corregir, anonimizar o eliminar información.
- Mantener una estrategia de respaldo y recuperación antes de usar la base con datos reales.
- Usar datos ficticios en desarrollo y pruebas; no cargar datos personales reales sin autorización y controles apropiados.
